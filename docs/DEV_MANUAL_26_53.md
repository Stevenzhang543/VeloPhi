# VeloPhi 26.53 开发手册

26.53 是一次架构重写：**前端 Vue，后端 Rust**。26.52 的仿真已经能在 Rust（WebAssembly）里跑，但界面线程上仍有大量 TypeScript 计算——观测量、情形识别、公式取值、事件详情、受力分析、纸带、曲线的降采样、编辑器的几何与位姿，以及被逐出内存的帧块的重算——它们都依赖 TypeScript 求解器。本版把这些计算全部移到 Rust，TypeScript 只负责界面与展示；桌面版的仿真改在原生 Rust 线程中运行。同时继续升级公式系统的查看方式（面板改版、公式时间轴、公式与画面联动），并处理 26.52 记下的两个物理遗留。原则、阈值与决策 D1–D64 继续有效。

**范围（2026-10-26，维护者确认）：** 维护者在 26.52 发布后提出 3 项要求：（1）继续升级公式系统，方便查看；（2）代码里仍有大量 TypeScript，希望“前端 Vue、后端 Rust”，进行一次重写，选最快、最不容易出问题的语言；（3）其他细节按现有手册继续。确认的选择：重写范围为“Rust 统一计算 + 桌面版原生 Rust”；TypeScript 求解器“移出应用，只留作测试参照”；公式查看做“公式面板改版”“公式时间轴”“公式与画面联动”三项。顺延到 26.54：链节绳、自定义公式卡、触屏与交互白板（D42）、无障碍（D43）、分享、插件接口。

## 1. 调研与实测依据（2026-10）

| 来源 | 结论 | 对 VeloPhi 的含义 |
| --- | --- | --- |
| 本仓库实测（26.52，35 个模板，`.cache/prof`） | 同一场景：TypeScript 求解器约为 WebAssembly 的 4 倍耗时；原生 Rust 比 WebAssembly 快约 1.46 倍（177 ms 对 259 ms）；识别、公式卡片、曲线在 TypeScript 中为毫秒到几十毫秒，但都要先在界面线程上编译一份 TypeScript 系统，被逐出的帧块也要用 TypeScript 重算（每块几十到几百毫秒，造成卡顿） | 计算全部用 Rust；界面线程用 WebAssembly（同步查询），桌面版的仿真用原生线程 |
| Tauri 2 IPC 通道（`tauri` 2.12.5 源码 `src/ipc/channel.rs`） | `Channel<InvokeResponseBody>` 发送 `InvokeResponseBody::Raw(Vec<u8>)` 时，前端收到 `ArrayBuffer`，不经过 JSON；通道保证顺序；命令也可以用 `ipc::Response` 返回原始字节 | 原生线程把 VRD1 增量容器原样发给页面，页面不解码，直接交给界面线程的 Rust 会话 |
| WebAssembly 线性内存增长（[TC39 resizable buffer](https://github.com/tc39/proposal-resizablearraybuffer/blob/master/README.md)、[memory.grow 与 ArrayBuffer](https://awesome.red-badger.com//chriswhealy/memory-grow-and-arraybuffers)） | `memory.grow` 会使旧的 `ArrayBuffer` 脱离（长度变为 0），已有的类型化数组视图失效 | 前端从不长期持有指向线性内存的视图：每次调用的结果复制出来（结果都很小）；帧数据按需取 |
| 静不定接触力（[Resolving Force Indeterminacy in Contact Dynamics](https://arxiv.org/pdf/1805.07437)、[Passive Reaction Analysis for Grasp Stability](https://arxiv.org/pdf/1801.06558)） | 刚体模型中冗余接触的约束力不唯一；常用做法是取最小范数解（伪逆），或加入变形协调条件 | V 形槽底静止时取最小范数解（D73），对称时即教材的对称解 |
| 26.52 实机检查记录（`docs/reports/26.52-windows-hand-check.md`） | V 形槽底静止时两侧摩擦力“夹紧”（f = μN）；组合后复合体原点有 10⁻¹² m 的舍入残差 | D73、D74 |

## 4. 本版新增决策

**D65 分层：前端 Vue，后端 Rust。** 规则：**凡是读写物理模型、状态或记录的计算都在 Rust 核心（`velophi-core`）中；TypeScript 只做界面与展示。**

- Rust 核心：求解器（已有）＋本版新增的会话（D66）与计算模块——观测量（含自定义量、接触力、能量账本）、情形识别与样本、公式取值与判定（表达式求值、量纲检查、逐步求值的中间值）、事件详情中的数值、受力分析图的力与分解、纸带点位、v–t 面积、题目答案与判分、预测目标、参数扫描、曲线降采样、画面视图（位姿、轮廓、绳路径、滑轮、接触点、力 / 速度 / 加速度箭头、频闪与轨迹采样）、编辑器几何（质量属性、多边形检查、轮廓、吸附用的运动学）、场景校验（变力表达式、多边形）、指纹。
- TypeScript：Vue 组件、画布绘制（几何由 Rust 给出）、标注避让与排版、单位换算与数字格式化（只用于显示）、多语文本与内联三语模板、由表达式树生成 LaTeX、导出打包（ZIP、PPTX、视频编码）。公式库的定义（标题、LaTeX、说明）与推导文本留在 TypeScript；其中参与计算的字段（表达式、单位、测量方式、适用条件）在启动时一次交给 Rust。
- 宿主：**界面线程**上的 WebAssembly 会话负责同步查询（滚动时间线、悬停读数都要求同步）；**仿真**在桌面版的原生线程（D68）或网页版的 WebAssembly 工作线程中运行；`velophi-cli` 增加 `calc` 子命令，供对照测试使用。
- 检查：测试遍历 `src/` 的全部模块，不允许引用 `tests/reference/`，不允许出现 `core/solver`、`core/observe`、`formula/situations*`；网页构建产物中不允许出现参照代码的特征串（如 `rebuildChunk`、`solveMode`）。

**D66 会话。** Rust 的 `Session` 是 26.52 `StreamRecording` 的移植：接收 VRD1 增量容器（字节原样，不在 JavaScript 中解码），保存全部检查点、帧块摘要、段与事件，帧块在内存预算内驻留（默认 512 MiB，最久未用的已关闭块先逐出）；读到被逐出块的帧时用检查点在同一线程同步重算（`rebuild_chunk`，同一条代码路径，逐位相同），重算结果按块摘要、事件与下一个检查点核对，不一致直接报错。远程预取保留：会话告诉页面哪些块即将用到，页面让仿真宿主（原生线程或工作线程）重算后交回会话安装（同样核对）。会话也计算有界运行的流式 `recordingHash` 与滚动指纹。会话持有编译好的系统、识别出的情形与公式库，所有查询都在会话上进行。没有记录时（编辑状态）用“场景会话”：只有场景与编译好的系统，提供初始位姿、轮廓与校验。

**D67 计算接口。** WebAssembly ABI 升到 2：保留 1 的运行接口（工作线程使用），新增 `session_create / session_apply / session_call / session_take / session_free` 与无状态的 `calc_call`。`session_call` 收一个 JSON 请求 `{ op, …参数 }`，结果是 VRD1 容器（JSON + 二进制块，大数组为 f64 块，不经 JSON）。操作清单、参数与结果格式写在 `engine/CALC.md`，前端的类型在 `src/engine/calc.ts`，两边由测试核对操作名。文本一律以消息 `{ key, params }` 返回（键为中文原文，沿用 `message.rs` 与 `MESSAGES.md` 的规定），由前端按界面语言渲染；`scripts/i18n-keys.mjs` 同时扫描 Rust 源码中的消息键。数字以 f64 原样返回，显示格式由前端决定。

**D68 原生桌面引擎。** `src-tauri` 直接依赖 `velophi-core`。命令：`engine_run_start(request, channel)` 在新线程中运行仿真，每个增量容器以 `InvokeResponseBody::Raw` 经通道发给页面；`engine_run_control(id, { until | stop | cancel | failBudget })` 控制前瞻、停止与取消（与工作线程协议相同）；`engine_rebuild(request)` 重算一个帧块（预取）；`engine_sweep(request, channel)` 并行运行参数扫描的各点（线程数 = 逻辑核数 − 1，至少 1；结果按点的序号排序，与顺序运行逐位相同）；`engine_info()` 给出版本与 ABI。页面通过 `src/engine/host.ts` 的“仿真宿主”接口使用它们：桌面版且命令可用时用原生宿主，否则用 WebAssembly 工作线程；宿主不同，结果逐位相同。原生运行的计时（墙钟预算）由 Rust 线程自己计；挂起的运行在窗口关闭时取消。

**D69 TypeScript 参照与一致性策略。** `src/core/solver`、`src/core/record`（帧与指纹部分）、`src/core/observe`、`src/formula/{situations, situations2651, measure, quadrature, elliptic}` 及事件详情、教学、分析、曲线降采样中的数值部分，移到 `tests/reference/`，保持 26.52 的代码，只做两类修改：本版的物理修正（D73、D74，两边同时改）与移出后需要的引用路径调整。对照：`scripts/parity.mjs`（求解器与记录，已有）与新的 `scripts/calc-parity.mjs`（计算模块：参照的 TypeScript 对 `velophi-cli calc` 的原生 Rust），覆盖全部模板、黄金场景与随机场景，逐位比较（文本比较消息键与参数）。参照中凡用到 `Math.sin/cos/exp/log/pow/atan2/hypot` 等的数值代码改用 `dmath`（与 Rust 一致；只影响末位，26.52 的显示不受影响）。前端测试在容器中通过 N-API 小程序调用原生库，在 Windows 发布构建中直接加载新构建的 WebAssembly，两者是同一份 Rust 源码。应用内的“自检”（D47）改为：原生 Rust 与 WebAssembly 在同一台机器上各算 35 个模板，比较指纹。

**D70 公式面板改版。** 面板顶部一行工具：搜索框（标题、符号、公式编号、情形名称；`/` 聚焦）、筛选（物体、类别：运动学 / 动力学 / 能量 / 动量 / 转动 / 碰撞 / 场与振动、判定：全部 / 一致 / 偏差 / 近似、只看收藏）、密度切换（紧凑 / 详细）、分组方式（按情形 / 按物体）。**紧凑**：每条公式一行——判定色点、标题、公式（缩小的 KaTeX）、理论值与仿真值、误差；点击展开为详细卡片。**详细**：26.52 的卡片。收藏（星标）的公式在出现时置顶，并在公式时间轴上单独标出；收藏、密度、分组与筛选保存在设置 `ui.formula` 中。键盘：↑↓ 在卡片间移动，回车打开详情，空格展开 / 收起，`f` 收藏。没有匹配时说明是哪个筛选条件排除了它们，并给“清除筛选”。卡片的数值来自 Rust：会话按时刻返回活动情形、各公式的理论值、仿真值、误差、判定、条件与逐步求值的中间值，前端只排版。

**D71 公式时间轴。** 主时间线下方的一条可折叠的轨道（默认展开，高度随情形数，最多 4 行，超出可滚动）：每个情形一段色条（按类别着色），事件型情形是一个竖线标记；段内按该情形的公式判定着色（全部一致为绿，有偏差为红，有近似为黄），收藏的公式另加星标。悬停显示情形名称、时间段与公式数；点击跳到该段起点（事件型跳到事件时刻），并把公式面板滚到该情形；双击放大时间线到该段。当前时刻的竖线与主时间线同步。数据由 Rust 一次给出（每个情形取代表时刻——事件型取事件时刻，其余取段中点——求一次全部公式的判定）。

**D72 公式与画面联动。** 悬停公式卡片：画布高亮该情形涉及的物体（描边加光晕），以及公式中出现的力（N、f、T、F弹 …）对应的箭头；悬停“已知量”中的一项：高亮对应的画面元素——物体（m、I、r）、接触（μ、N、f）、绳与弹簧（T、k、L₀）、角度（θ：在斜面上画角弧）、速度（v：画速度箭头）。在公式页签中点击画布上的物体：公式面板按该物体筛选（再点空白处取消）；点击力箭头：筛选含该力的公式。映射由 Rust 给出：每个样本变量带“引用”（类型与对象编号：body / pair / rope / spring / connector / angle / velocity），每个情形带物体列表；前端只按引用查画面元素。

**D73 静不定接触取最小范数解。** 求解某个模式的约束力时，若约束行线性相关（秩不足）且方程相容，完全主元消元给出的“基本解”（无主元列的未知量取 0）改为最小范数解：由消元结果得到零空间基 Z（每个无主元列一列），λ = λ_b − Z (ZᵀZ)⁻¹ Zᵀ λ_b。只在秩不足时多算这一步，满秩的场景结果逐位不变。V 形槽底静止的小球因此得到 f₁ = f₂ = 0、N₁ = N₂ = mg/(2 cos θ)（两侧都粘着的模式满足摩擦锥而被选中）。两个引擎同时修改；含冗余接触的模板（V 形槽）的指纹与夹具更新，记入发布说明。

**D74 组合与切割的坐标取整。** 组合（复合体）与切割得到的位置、局部坐标与角度按切割工具的规则取整到 10⁻⁹ m（角度 10⁻⁹ rad）后写入场景，不再出现 2×10⁻¹² m 这样的残差；质量属性由取整后的几何重新计算。

## 6. 验收

| 项 | 标准 |
| --- | --- |
| 分层 | `src/` 中没有求解器与数值模块（测试检查引用与目录）；网页构建产物不含参照代码的特征串；界面中所有数值来自 Rust |

## 8. 实施记录与决策修订（2026-10-27）

实现中对第 4 节的几处决策做了修订或补充，以此为准：

- **D66/D67 实现**：会话 `engine/velophi-core/src/session.rs`，操作分派 `api.rs`（会话）与 `calc.rs`（无状态），操作清单 `engine/CALC.md`，ABI 2 见 `engine/ABI.md`。运行驱动（创建、前瞻暂停、推进、增量、结束、停止、取消、预算、帧块重算）统一为 `velophi-core/src/driver.rs`，WebAssembly、原生桌面引擎与 N-API 测试模块共用。`tests/engine/ops.test.ts` 核对前端发送的操作、Rust 实现的操作与 `CALC.md` 三者一致。
- **D68 修订**：没有单独的 `engine_sweep` 命令。参数扫描（`src/analysis/sweep.ts runSweep`）同时运行多个点（原生引擎时为逻辑核数 − 1，至少 1），每个点经 `engine_run_start` 在自己的线程中计算；结果按点的序号报告，与顺序运行逐位相同。原生运行的作业逻辑在新 crate `engine/velophi-native`（不依赖 Tauri），`src-tauri` 只把它接到命令上。经 IPC 的 JSON 会丢失 −0、NaN 与 ±∞，所以场景以 `sceneText`（−0 写作 "-0"，与 `jsonBytes` 相同）、检查点以 `checkpointHex`（小端 f64 的十六进制）传递，保证原生与 WebAssembly 逐位相同。窗口销毁时取消全部原生运行；页面通道失效时运行自行结束。
- **D69 补充**：参照代码在 `tests/reference/`（求解器、记录、观测、识别、测量、公式取值、事件详情、`views.ts`：画面视图、受力分析图、纸带、面积、箭头比例）。`scripts/calc-parity.mjs` 覆盖记录、观测量、情形与样本、公式卡片、事件详情、帧视图、受力分析图、纸带、面积与箭头比例，逐位比较。26.52 的画布把变力画成场景中的常量值（表达式力的当前值没有画出），26.53 两边同时改为当前值。
- **D72 修订**：已知量与画面元素的对应（物体、接触、绳与弹簧、角度、速度、重力）由前端根据变量名与情形的物体列表推断（`src/formula/panel.ts varRef`），不涉及任何数值；公式涉及的力由公式的左边与所用系数推断（`forceKindsOf`）。画布上点击力箭头的命中检测在渲染器中（`forceArrowAt`）。
- **D73 修订**：最小范数解对 V 形槽并不给出教材解——两侧接触力的最小范数解是每侧一个竖直的 mg/2（f = mg·sinθ/2）。改为**分两级**的最小范数：在全部解中先使粘着摩擦力的平方和最小，再在剩下的自由度中使其余约束力的平方和最小（冗余支撑平均分担）；两级依次在零空间中求解（`linalg.rs min_norm_correction`），所选解若需要拉力接触、推力绳或端挡、超出摩擦锥或滚动阻力限度（容差同模式判定）则保留基本解（`dynamics.rs force_excess`）。**只在静止状态使用**（全部速度分量 ≤ 10⁻⁷）：运动中仍用 26.52 的基本解。原因见下面的实测：运动中改选约束力会改变接触何时开始滑动（轨迹随之改变），而在一步之内切换选法会使右端函数跳变。另外，26.52 中小球停在槽底时选中的是“一侧滑动（vt = 0）+ 一侧粘着”：投影前该侧切向速度略大于 10⁻⁷ m/s，粘着不在候选中；投影后它已静止。现在投影后若某个滑动单元的切向速度降到 10⁻⁷ m/s 以下而投影前没有，则在投影后的状态重新确定模式（两个引擎同时修改）。结果：槽底静止时 f₁ = f₂ = 0，N₁ = N₂ = mg/(2 cos θ)（相对误差约 10⁻¹⁵）。指纹改变的夹具：V 形槽、活动斜面；其余 41 个夹具场景不变。
  - 实测经过：第一版用一个加权系统（摩擦行权重 10¹²、其余为 1）且不分运动与静止。与 26.52 的引擎逐个比较 2000 多个随机场景时发现：第二级被相对主元容差吞掉、剩余自由度的取法随主元选择跳动；最小摩擦解常需要拉力接触，使一类接触组合的每个模式都被判为不相容，模式搜索每次穷举上千个模式（一个场景从 0.23 s 变为 25 s）；约束力发散的“卡死”构型不再很快以“状态不再有限”结束，而是以极小步长算到 5×10⁶ 步。改为分两级并加可行性检查后，又有场景因选法在步内切换而步长崩溃（0.11 s → 108 s）。限制为静止状态后：2055 个有限时长场景（模板、黄金场景、四类随机场景，两个种子）的结局（完成 / 出错、停止原因、帧数）与 26.52 全部相同，1909 个指纹逐位相同，没有场景慢 3 倍以上，总耗时 101 s 对 106 s。
- **D74 实现**：`src/app/editor/geometry.ts q9`；切割、组合、拆分写入的位置、局部坐标、角度、锚点与滑轮位置都取 10⁻⁹ 的整数倍。
- **其他**：网页工作线程在一个帧块计算超过 250 ms 时补发未完成块的帧（26.53 早期改写中丢失了这一行为，已恢复）；核心的场景错误（`scene.*`）此前只有 TypeScript 校验给出文字，现在核心报告时也按界面语言显示（`src/i18n/coreText.ts`）；`scripts/i18n-keys.mjs` 同时扫描 Rust 源码与 `coreText.ts` 中的文字。
- **无头浏览器检查后的修正（网页版，WebAssembly 引擎）**：① 误差列不再显示 `0.0e+0`：0 显示为 0，≥ 0.001 % 显示百分比，更小的写成 m×10⁻ⁿ。② 悬停卡片时只点亮公式变量涉及的物体（质量、接触系数、角度；公式不涉及任何物体时点亮整个情形），木板下面的地面不再随“物块的加速度”一起发光；公式用到 θ 时同时画出角度。③ 速度、加速度与力的数值标签互相避让（同一接触点的作用力与反作用力原先重叠成一团）。④ 详细模式的卡片在 380 px 宽的面板中不再横向溢出（`Section` 内容区可以收缩）。⑤ 监视页隐藏时仍持有上一次的运行；切换模板后该运行的会话已释放，监视列表变化会读到它并报错“session already freed”——现在隐藏页在其运行被替换后改为空，显示时再读新运行（这是 26.52 就有的问题）。⑥ 公式时间轴上没有可比较公式的情形只画轮廓。⑦ 持续计算时时间轴工具栏在 1080 px 以下隐藏帧号与按钮文字，“已算到”不再被截断。⑧ 切换模板后公式时间轴停在第一次识别的结果上：缓存只以帧数与事件数为键，运行已暂停在前瞻目标时帧数不再变化，之后更完整的识别结果被忽略；现在缓存同时比较情形列表。
